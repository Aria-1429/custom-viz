# DPX

> ⚠ **リリース前（v0.1.0）です。** `0.x` の間は破壊的変更を予告なく入れることがあります。

**Splunk 上で動く完全独自のダッシュボード基盤**（アプリ ID: `dpx`）。
Dashboard Studio でも classic（Simple XML）でもなく、独立 React ページの上に自前の
ダッシュボードエンジンを載せたものです。「Splunk 上で動作し、Splunk にサーチが投げられる」
ことだけを前提に、**より映えるダッシュボードを自由に簡単に作れる**ことを目指しています。

実装ナレッジ（構成・スキーマ・viz の作り方・踏んだ罠・E2E ツール）は
[.claude/skills/splunk-viz/references/dpx-platform.md](../../.claude/skills/splunk-viz/references/dpx-platform.md)
に集約しています。**着手前にそちらを読むこと。**

## 構成（30秒版）

```
Splunk Web
 └ ホストビュー dpx（画面はこの1枚だけ。template="pages/splunk_ui_app.html" ＝ Splunk 同梱）
    └ pages/dpx.js                        ← 唯一のランタイム（ホーム＋ダッシュボード）
        /app/dpx/dpx            → ホーム（一覧）
        /app/dpx/dpx?id=<app>/<name> → ダッシュボード
 └ 定義ビュー（1 ダッシュボード = 1 ビュー XML。isVisible=False の入れ物）
    └ <definition><![CDATA[ DPX スキーマ v1 の JSON ]]></definition>
```

- 保存形式は Studio と同型（ビュー XML に定義 JSON を埋め込む）。REST で動的に作成できる
- **画面間は SPA 遷移（pushState）＝ページ再読込ゼロ**。ボード切替・ホーム往復に白は出ない
- viz は「props を受け取る素の React コンポーネント」を `vizRegistry.js` に登録するだけ
  （iframe なし・config.json なし・splunkd 再起動なし）
- **カスタム Mako テンプレートは不使用**（10.4.0 非推奨・AppInspect 4.4.0 から審査 fail の対象）。
  検討した代替案と全数調査の記録は dpx-platform.md §1.1 を参照

## サンプルダッシュボード

| ファイル | 用途 |
|---|---|
| [`examples/aegis-soc.json`](examples/aegis-soc.json) | **ショーケース**。DPX でしか組めない構図を一枚にまとめたもの（下記） |
| [`examples/all-viz-check.json`](examples/all-viz-check.json) | 全 viz の描画確認用（30枚を並べただけ） |

### AEGIS / Global Threat Operations（ショーケース）

3タブ・25パネル・21データソース・14種の viz。**Studio では組めない**要素を意図的に集めてある:

- **左サイドバータブ**（`tabPosition: "left"`）
- **背景エフェクト**（`constellation`）がパネルの裏で常時動く
- **枠なしパネル**（`frameless`）で見出しと時計を地の上に直接置く
- **全幅の地図を1枚のキャンバスとして使う**（`frameless` + 12列。枠もタイトルバーも無い）
- 自作 viz（world-map / attack-globe / sunburst / sankey-flow / heat-matrix /
  timeline-swimlane / liquid-tube）とネイティブ viz を混在

⚠ **地図（world-map / attack-globe）の上に他のパネルを重ねない。**
DPX は `style.z` でパネルを重ね置きできる（Studio に無い機能）が、
**地図に対して使うと肝心の地形と着弾点が隠れる**。
重ねたガラスパネルは見栄えはするものの、地図の凡例・フロー一覧・
端の国（日本／オーストラリア）が読めなくなった（実機で確認して取りやめ）。
**重ね置きは「地図以外」で使う。** 地図は単独で全幅を与えるのが正解。

投入:

```bash
node tools/dashboard-loop/src/push.mjs apps/dpx/examples/aegis-soc.json --name dpx_aegis
```

⚠ **`makeresults format=csv` の CSV は本物の改行で書く。**
`\n` の2文字を埋め込むと**1行の壊れた CSV**になり、
**HTTP 200 のまま 0 行**が返る（エラーにならないので気づきにくい）。
⚠ **`eval` で日本語のフィールド名を参照するときは `'達成率'` と単引用符で囲む。**
囲まないとこれも **200 で 0 行**になる（このダッシュボードの作成中に実際に踏んだ）。

## できること・できないこと

### 見た目の 4 軸（Design Engine）

ダッシュボード全体の見た目を、独立した 4 つの軸で切り替えられます。
どの組み合わせも成立します（「ダーク × Liquid Glass × 水彩 × スプリング」など）。

| 軸 | 設定 | 選択肢 |
|---|---|---|
| Theme（配色） | `style.preset` | 18 プリセット |
| Surface（面の質感） | `panel.style.variant` | 25 種 |
| Brush（線と塗り） | `style.brush` | なし / 色鉛筆 / クレヨン / 水彩 / インク / マーカー |
| Motion（動き） | `style.motion` | なし / 控えめ / スプリング / オーガニック |

編集パネルの「デザイン」から選べます。

### ⚠ 画材（Brush）の効き方は viz によって違う

**同じ設定でも、DPX ネイティブ viz とカスタム viz で結果が変わります。**

| viz | 経路 | 見た目 |
|---|---|---|
| **DPX ネイティブ**（棒・折れ線・ドーナツ・ランキング） | 描画 API（rough.js） | **塗りにハッチングが入る**（別物になる） |
| **カスタム viz（SVG 描画）** | SVG フィルタ | **輪郭が揺れるだけ**（塗りはベタのまま） |
| **Canvas / WebGL**（Attack Globe・World Map 等） | — | **既定で対象外**（文字が焼き込まれ分離できない） |
| **HTML div 描画**（Gradient Bar・Liquid Tube 等 5 件） | — | **未対応**（SVG 形状が無く自動検出が届かない） |

⚠ フィルタ経路は**原理的に塗りを変えられません**（変位マップは既にある絵を
ずらす処理なので、ハッチングを作れない）。強度を上げても輪郭の歪みが増えるだけです。

**塗り感まで揃えたい場合**は、その viz の描画コードを rough.js に差し替える
必要があります（`design/brush/brushes.js` に `brushArc` 等を実装済み）。
ただし **viz が DPX に依存する**ため、Studio では動かなくなります。

### 画材を viz 側で細かく制御する

自動検出の結果を変えたいときは、その要素に属性を 1 つ足します。
**例外だけ書けばよく、全部を宣言する必要はありません。**

```jsx
<line ... data-dpx-ink="none" />   {/* この要素だけ画材から外す */}
<path ... data-dpx-ink="mark" />   {/* この要素も画材の対象に加える */}
```

⚠ Studio では**未知の `data-*` 属性として無視される**ので、両対応は壊れません。

### [1.2.0] - 2026-08-15

#### 追加

- **`dpx.markdown`（マークダウン）** … Studio の `splunk.markdown` の代替。
  **実測（Studio のバンドルから schema を抽出）**: 標準版のオプションは
  `markdown` / `fontSize` / `fontFamily` / `rotation` の **4 つだけ**で、
  説明文も「Add text using **basic** markdown syntax」。こちらは:
  - **GFM 対応**（`remark-gfm`）＝ **表・打ち消し線・チェックリスト**が書ける
  - **`$トークン$` に加えて `$列名$`** でサーチ結果の1行目を差し込める
  - **テーマ連動の配色**（プリセットを変えると見出し・表・コードの色も追従）
  - 文字サイズ5段階／文字揃え／ブロック配置／最大幅／余白
  - ⚠ **生 HTML は通さない**（`rehype-raw` を入れない＝XSS 対策）。
    `rotation` は**作らない**（回転した本文は読めない）
- **画材（Brush Engine）を `dpx.gauge` / `dpx.progress` / `dpx.histogram` に適用**。
  ⚠ **`dpx.heatmap` / `dpx.value` / `dpx.status` / `dpx.table` には入れない**
  （セルが小さい・**文字を読ませるのが本体**の viz は、線が乗ると値が読めなくなる）

#### 修正

- ⚠ **ライト系テーマでマークダウン本文が見えなかった**。Splunk のページ側に
  `h1, p` を白にする**インラインのグローバル CSS** があり（DPX の外・変更不可）、
  親要素にだけ色を置くと **`<p>` だけ白のまま**残る。
  → テキストを持つ要素すべてに明示指定して上書き。
  **太字だけ読めるので「行が重なっている」ように見え、誤診しやすい**
- ⚠⚠ **`$列名$` の差し込みが効かず、`$綴り間違い$` も黙って消えていた**
  （実機で発覚）。本文の `$...$` はトークンと列名で構文を共有しており、
  **先に走るトークン展開が「未設定なら空文字」を全名前に適用**していたため、
  列名が後段の `applyFieldValues` に届く前に消えていた。
  → 「**列名**」と「**宣言のないトークン＝書き間違い**」を空文字化の対象から外した。
  書き間違いは `$typo$` のまま画面に残るので**気づける**。
  ⚠ ASCII 列名だけの不具合（トークンの正規表現が ASCII 限定のため、
  `$ホスト$` のような日本語列名は**偶然動いていた**）＝**片方だけ試すと見逃す**

### [1.1.0] - 2026-08-15

**標準チャートを 7 種 → 11 種に増やした。** 既存 viz の挙動・見た目は変えていない。

これまでの 7 種は「合計・推移・構成比・順位・表・状態」を担当していたが、
**「分布」「2 軸の密度」「目標に対する到達度」を出す手段が無かった**。
SPL 側で `| stats count by range` を書いて棒グラフに流す、といった
回避が必要だったものを viz 側で吸収する。

#### 追加

- **`dpx.gauge`（ゲージ）** … 上限に対する到達度を弧で見せる。3/4円 / 半円、
  ％表示、カウントアップ。**目標値はデータの 2 列目が優先**（SPL で動かせる）。
  単一値（`dpx.value`）と違い「満タンが意味を持つ」指標向け（SLO・使用率）
- **`dpx.progress`（進捗バー）** … 項目ごとの達成率。**項目ごとに目標が違ってよい**
  （3 列目）。ランキングが「項目どうしの相対比較」なのに対し、こちらは絶対達成率。
  ⚠ 100% 超は色で警告しつつ、**数字は実値のまま**出す（丸めて隠すと事故に気づけない）
- **`dpx.histogram`（ヒストグラム）** … 値のばらつきを見る。**ラベル列が要らない**。
  階級分けは viz 側（スタージェスの公式で自動）＝**画面で切り方を変えられる**
- **`dpx.heatmap`（ヒートマップ）** … 「曜日 × 時間帯」のような 2 軸の交差を濃淡で。
  ⚠ **欠測は枠だけで描く**（薄い塗りにすると「値が小さい」と誤読される）
- **`viz/aggregate.js`（集計）** … 階級分け・クロス集計の純粋関数。依存ゼロで
  `test/nativeViz.test.mjs` から検証する（境界値は目視で判定できないため）

#### 修正

- ⚠ **空データで `d.column(0)` を呼ぶと落ちていた**（`EMPTY_VIZ_DATA` に
  `column()` が無かった）。viz は**フックのルール**により `useMemo` を

  空の戻り値にも `column()` / `columnByName()` / `rows()` を生やした
  （実機で 3 つの viz が同時に落ちて発覚）

### [1.0.1] - 2026-08-15

**タブ切替の重さを直した。** 見た目は 1 ピクセルも変えていない
（実機のスクリーンショットを画素比較して 480 万サブピクセル中 **差分 0** を確認）。

きっかけは「タブ 2 を開くとき若干重たそう」という報告。**推測でコードを触らず、
先に CDP トレースで内訳を取った**ところ、原因は描画そのものではなく
**タブを切り替えるたびに全部を作り直していたこと**だった。

#### 修正

- **同じサーチを何本も投げないようにした**（`data/searchStore.js` を新設）。
  共有データソースは「編集時に SPL を 1 か所へまとめる」だけの仕組みで、
  **実行時には共有されていなかった**（`resolvePanelSearch` は文字列を組み立てる
  純粋関数で、実行はパネルごとの `useSplunkSearch` が個別に行っていた）。
  同じデータソースを参照する N 枚のパネルが**同一 SPL のジョブを N 本**投げていた。
  → SPL＋時間範囲＋名前空間をキーに **実行中のジョブへ合流**し、
  **完了した結果を 30 秒間キャッシュ**する層を挟んだ。
  自動更新（`refresh`）のタイマーも購読者ごとではなく **1 本にまとめ**、
  購読者間で最短の間隔を採用する。
- **一度開いたタブを DOM に残すようにした**（`renderer/DashboardRenderer.jsx`）。
  従来はタブ外のパネルを配列から落としていた（＝React が丸ごとアンマウント）ため、
  戻るたびにサーチ・手描き枠・出現アニメが全部やり直しになっていた。
  → **タブごとに 1 つのグリッド**を持ち、非表示のものは `display:none` で残す。
  ⚠ 最初から全タブは描かない（初回表示で全タブぶんのサーチが走ると本末転倒）。
  **開いたタブだけを覚えて以後残す**ので、初回のコストは変わらず 2 回目以降が速い。
- **手描き枠の二度描きを止めた**（`renderer/HandDrawnFrame.jsx`）。
  `ResizeObserver` は `observe()` した瞬間に必ず 1 回発火するため、
  `draw(); ro.observe(box);` は**毎マウント 2 回**描いていた。
  → 直前に描いたサイズを覚えて、同じなら描き直さない。
- **紙の目（tooth）の無駄描きを止めた**（`design/handDrawn.js`）。
  枠の帯だけを `clip('evenodd')` で塗っていたが、
  **クリップはフラグメントを捨てるだけでループ回数は減らない**ため、
  面積比例の粒の大半を「描いた直後に捨てて」いた。
  → `band` を渡すと帯の外に落ちる粒を**描かずに飛ばす**。
  ⚠ **乱数列は 1 つも飛ばさない**（座標を引いてから判定する）。
  ここで早期 continue すると残った粒の位置まで変わって見た目が変わる。
  テストで「描かれる粒が band 無しと完全一致」を機械的に固定した。

#### 実測（実機 dpx/test のタブ 2・4 パネル・1600×1000）

| | 修正前 | 修正後（初回） | 修正後（再訪） |
|---|---|---|---|
| `search/jobs` POST | **4 本** | 0〜1 本 | **0 本** |
| canvas 描画 | 8 回 | 4 回 | **0 回** |

| 安定までの時間 | 953ms | 692ms | 644ms |

#### 修正（コールド入口の白フラッシュ）★

**「HTML が来てから 800ms、前のページが出たまま」だったのを 96ms にした。**
Splunk の他ページは明るいので、これが「白フラッシュ」として見えていた。

- **原因は暗転処理の置き場所**。標準テンプレートは「ビュー名と同名の JS」を 1 本だけ
  読むので、そこにアプリ全体（**4.88MB**）を詰めていた。`bootPaint`（地を暗くする処理）を
  **先頭の import** に置いても、**モジュール評価はバンドル全体の取得＋パースが
  終わるまで始まらない**（実測 800ms）。
- → **エントリを 6.4KB のシムにして、本体を動的 import に**（`pages/dpx/index.jsx`）。
  テンプレートが読む JS は 1 本のまま＝同名 JS 規則は満たしたまま。
  - `__webpack_public_path__` は**実行時に**自分の `<script src>` から逆算する
    （Splunk の静的 URL は `_bump` のたびにキャッシュキーが変わるため固定できない）
  - チャンク名を固定（`chunkIds:'named'` ＋ vendor 分割の停止）。
    ⚠ 既定の数値 ID は**モジュールグラフが変わると番号がずれ**、
    `appserver/static` は上書きしても**古いファイルが消えない**ので孤児が積み上がる

  | | 修正前 | 修正後 |
  |---|---|---|
  | `dpx.js` | 4.88MB | **6.4KB** |
  | bootPaint 実行 | 800ms | **85ms** |
  | first-paint | 808ms | **96ms** |
  | 遷移直前の白（0.05s 刻み） | **8 フレーム（~0.8s）** | **1 フレーム（~0.05s）** |

- ⚠ **残る 1 フレームは消せない**（HTML 応答 26ms 〜 JS 評価 85ms の間）。
  ここを塗るには初期 HTML の `<head>` が要る＝Mako の話に戻るので、実用上は許容と判断。
- ⚠ **旧ナレッジの「HTML 表示〜JS 開始は構造上塗れない」は誤りだった**と訂正済み
  （`references/dpx-platform.md` §1.2）。塗れないのではなく、
  **塗る処理を巨大バンドルの後ろに置いていた**のが原因。

#### 変更（Renderer の内部分割）

性能改善で `DashboardRenderer.jsx`（1,609 行）に手を入れた際、
**タブの生存管理を `useState` で書き足してしまった**——State 層を独立させた
設計に逆行する形だったので、同じ版のうちに整理した。

- **タブの生存管理を純粋関数へ**（`renderer/tabLifecycle.js`）。
  「どのタブを DOM に残すか」を React から切り離し、方針をテストで固定した:
  **初回は開いたタブだけ**（全タブを描くと初回が重くなる）/ **LRU で上限 8 枚** /
  **定義から消えたタブは捨てる**（隠れた DOM でサーチが回り続けるのを防ぐ）/
  **表示中のタブは絶対に落とさない**。
  ⚠ 消えたタブの掃除は、当初の `useState` 版には**無かった**（このとき見つけた）。
- **タブ 1 枚ぶんのレイアウト解決を純粋関数へ**（`renderer/tabLayout.js`）。
  区画の見出し行の挿し込みは「ずれると罫が見出しに重なる」見た目の事故に
  直結するのに、これまで機械的な検査が無かった。**19 件のテストで固定**。
- **`Panel` を独立ファイルへ**（`renderer/Panel.jsx`・647 行）。
  ⚠ 分けた理由は「長いから」ではなく**関心が違う**から:
  Panel =「1 枚をどう描くか」/ Renderer =「どう並べるか」。
  実際、両者が共有していたのは**寸法とアニメ表の定数だけ**（`rendererConst.js` へ集約）で、
  状態の共有はゼロだった＝**元から独立していたものが同居していた**。
- **層の境界をテストで固定**（`test/layers.test.mjs` に 4 件追加）:
  Panel → Renderer の循環参照禁止 / Renderer が viz 解決を持たない /
  寸法・アニメ定数の定義は 1 か所 / 生存判定とレイアウト解決は React 非依存。
