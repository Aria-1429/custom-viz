# カスタム viz の描画パフォーマンス（実機計測に基づくナレッジ）

`/splunk-viz` スキルの参照ナレッジ。**「viz が重い／大画面で fps が落ちる」要件を受けたら
コードを触る前にこれを読む。** 2026-08-09、world-map v2.1.0 の大規模改善
（4パネル・1080p で 5.9fps → 60fps、実ユーザーの 4K 実機でも「スムーズ」を確認）で
確定した知見をまとめる。**すべて実機計測済み**（推測の項目はその旨明記）。

計測環境: Splunk 10.4.2 / headless Chromium（**SwiftShader＝ソフトウェアレンダリング**。
絶対値は実 GPU より悪いが、相対比較と機序の特定には有効）。

---

## 1. 鉄則: 推測で直さない。先に内訳を取る

「重い」と言われたら**必ず CDP トレースで内訳を取ってから**手を入れる:

```bash
cd tools/dashboard-loop
SPLUNK_APP=dashboard_loop_test node measure-breakdown.mjs <dashboard> 2560 1440 5   # カテゴリ別内訳
SPLUNK_APP=dashboard_loop_test node measure-viewport.mjs  <dashboard> 3840 2160 5   # 解像度を変えて計測
SPLUNK_APP=dashboard_loop_test node measure-fps.mjs       <dashboard> 5             # rAF 間隔
```

- **`RasterTask`（数千ms）≫ `FireAnimationFrame`（数十ms）なら、犯人は JS ではなく
  「半透明の大きな塗り」**。JS を最適化しても 1fps も変わらない。
- **解像度だけを変えて測る**と「本数の問題か、面積の問題か」が切り分けられる。
  world-map は弧30本固定で 1280×720=13fps / 2560×1440=3.5fps ＝ 面積が支配的だった。
- 対策は**1つずつ入れて毎回計測する**。今回の作業では「効くはず」と入れた対策のうち
  **3つが無効・1つが逆効果**だった（§5）。計測せずに積んでいたら原因を見失っていた。

## 2. 犯人の類型 =「面積に比例する半透明の塗り」

コストが**パネル面積 ×（毎フレーム）**で効くものが諸悪の根源。大画面ほど致命的になる。
world-map で1つずつ外して計測した寄与（2560×1440・弧30本・4面）:

| 犯人 | 症状 | 寄与（実測） | 対策 |
|---|---|---|---|
| **要素ごとの SVG `feGaussianBlur`** | 弧のグロー等。要素数×フィルタ領域を毎フレーム再ラスタライズ | 3.5 → 12.2fps | フィルタ全廃。太さ・不透明度の違う**実線の重ね**で発光を代替 |
| **巨大パスの半透明塗り** | 陸地グロー層（大陸シルエット全体） | 7.4 → 23.3fps | **層ごと廃止**（輪郭は細いストロークで足りる）。⚠ぼかし→太い半透明ストロークへの置き換えは**逆に重い** |
| **SMIL `<animate>` でジオメトリを動かす** | `r` 等を動かすと**レイヤー全体**が毎フレーム再ラスタライズ | 22.1 → 26.1fps（単体） | ジオメトリを動かさない。CSS transform/opacity か Canvas へ |
| **大きな radialGradient 円**（SVG） | CSS transform アニメでコンポジタ処理にしても合成が重い | 21.6 → 48.1fps | **毎フレーム描いている Canvas に相乗り**させる（レイヤーが増えない） |
| **`backdrop-filter: blur()`** | 下のアニメが動くたび毎フレーム再ブラー。**文字のサブピクセルAAも無効化**（＝小さい文字がぼやける） | 26.5 → 45.7fps | 全廃して**背景の不透明度を上げる**（0.92〜0.96。ガラス感は色味と影で残す） |

⚠ 過去に「backdrop-filter の寄与は7%」と計測していたが、それは SVG フィルタが支配的だった
頃の値。**ボトルネックを潰すたびに他の寄与は再計測しないと嘘になる。**

## 3. アニメーションの土台（world-map の最終形）

- **WebGL2 / Canvas 2D のハイブリッド**:
  - 実 GPU → **WebGL2**。帯・リップル・グローを全て「位置＋頂点色の三角形」に落とし、
    1シェーダ・1バッファ・1 drawArrays。**面積スロットル無し（4K でも 30fps 狙い）**
  - ソフトウェア GL（SwiftShader / llvmpipe）→ **Canvas 2D＋面積スロットル**。
    **ソフトウェア環境では WebGL にしても速くならない**（実測: 1080p で 2D 60fps / GL 51fps。
    4K の床は「dirty な canvas の表示解像度での合成」で、静止時は 4K でも 60fps）
  - 判定は `WEBGL_debug_renderer_info` の文字列。⚠ **必ず使い捨て canvas で判定する**
    （一度 webgl2 を取った canvas では `getContext('2d')` が二度と取れない）
  - 経路確認は console の `[world-map] flow renderer:`／強制はスキーマ外オプション `forceRenderer`
- **画面外・非表示は rAF 完全停止**（IntersectionObserver + visibilitychange）。
  同一オリジン iframe はメインスレッド共有＝見えないパネルも他パネルを遅くする
- **`animDuration=0` は rAF ループ自体を起動しない**（「回して描画スキップ」は CPU を食う）
- **本数に応じた品質段階**（〜120本: 30fps フル / 〜400本: 20fps / 超: 15fps・グロー省略）
- **固定ステップ時刻**（実時間追従だと遅延フレームで光が跳ぶ。等量で進めれば
  「全体がわずかに遅くなる」だけで跳ばない）
- Canvas 2D の内部解像度キャップは**塗り面積には効くが合成には効かない**
  （実測: 上限を下げても fps 不変）。減らせるのは「描く回数」だけ

## 4. UI 操作は「再レンダリングゼロ」で

ドラッグ移動・リサイズ（world-map のフロー一覧で実装）:
- **操作中は React を通さず DOM の style を直接書く**。保存（setOptions）は**離した時に1回だけ**
- 実測で 60fps 維持（200行のテーブルをドラッグしても再レンダリングが起きない）
- クリックとの区別は移動量しきい値（4px）＋ドラッグ直後の click を1回だけ握りつぶす

## 5. 効かなかった対策（棄却済み。再提案しない）

すべて実機計測で棄却:
- **canvas 内部解像度の上限**（合成コストは表示面積で決まる。1fps も変わらず）
- **`will-change` によるレイヤー昇格**（要素数ぶんレイヤーが増え **22.1 → 17.4fps と悪化**）
- **帯のサンプル点数削減**（頂点数はコストではなかった。誤差）
- **ぼかし → 太い半透明ストローク代替**（巨大パスでは塗り面積が減らず逆効果。§2）
- ソフトウェア GL 環境での **MSAA**（antialias:true）は 57.6 → 43fps と高価。
  実 GPU では実質無料なので、GL 経路（＝実GPU限定）では on のまま

## 6. 計測・検証ツール（tools/dashboard-loop/）

| ツール | 用途 |
|---|---|
| `measure-fps.mjs` | トップフレームの rAF 間隔（全パネル合算の体感 fps） |
| `measure-viewport.mjs` | 解像度別の fps（面積依存の切り分け） |
| `measure-breakdown.mjs` | CDP トレースのカテゴリ内訳（RasterTask vs JS） |
| `probe-renderer.mjs` | webgl2 / canvas2d どちらの経路かを console から確認 |
| `probe-drag.mjs` / `probe-resize.mjs` | 実マウスでのドラッグ／リサイズ検証 |

計測用ダッシュボード（dashboard_loop_test に残置）: `wm_p_light`（弧30本×4面）/
`wm_p_anim`（300本×4面）/ `wm_p_gl`（GL強制）/ `wm_ui`（テーブル・凡例あり）。

⚠ 実マウス検証の罠: **Playwright の実マウスが「合成イベントでは動くのに実マウスで
動かない」ときは、親ドキュメントのオーバーレイ（Splunk のパネルホバーツールバー等）が
pointerdown を横取りしている**。パネル右下は特に被りやすい（実機で確認）。

## 7. 環境の注意

- 開発機（GPU 無し・SwiftShader）の数値で **GPU 向け最適化を評価しない**（逆も同じ）。
  ソフトウェア環境の 4K はどう最適化しても合成の床（〜10fps）がある
- 実 GPU での改善は機序＋RTX 5080 の既知実測（webgl2 全画面シェーダ 62fps）に基づき、
  **ユーザーの 4K 実機で「スムーズ」を確認済み**（2026-08-09）
- ノート PC の内蔵 GPU でもこの GL 負荷（数万頂点・1draw）は軽い（機序からの推測。
  GPU が効かない環境は自動で 2D 経路に落ちるため実害はない）
